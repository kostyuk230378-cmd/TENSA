## Документация для GLM 5.3: `05-rollback.md`

```markdown
# Руководство для GLM 5.3 — Откат

**Версия:** 0.1.0
**Дата:** 2026-10-06
**Статус:** Откат

---

## Назначение

Этот документ описывает, как GLM 5.3 должен откатывать изменения,
если что-то пошло не так. Цель: минимизировать ущерб, восстановить
рабочее состояние, не потерять данные.

---

## Принципы

### 1. Откат — часть процесса

Откат — не «провал», а нормальная часть разработки. Лучше откатить
и переделать, чем оставить сломанный код.

### 2. Откат — быстрый

Чем быстрее откат, тем меньше ущерб. Git — основной инструмент.

### 3. Откат — безопасный

Откат не должен ломать данные пользователя. Если ломает — сначала
бэкап.

### 4. Откат — документированный

Каждый откат — с объяснением: что, почему, как.

### 5. Откат — не отменяет обучение

После отката — анализ: почему не получилось, как избежать.

---

## Когда откатывать

### 1. CI не проходит

- Тесты падают.
- Clippy warnings.
- Сборка не компилируется.
- Покрытие ниже порога.

**Действие:** исправить или откатить.

### 2. Ревью отклонено

- Архитектор нашёл критичные проблемы.
- Решение не соответствует ADR.
- Нарушен контракт.

**Действие:** исправить или откатить.

### 3. Регресс

- Новая версия ломает старую функциональность.
- Пользователи сообщают о багах.
- Производительность упала.

**Действие:** откатить, проанализировать.

### 4. Критичный баг в production

- Утечка данных.
- Потеря данных.
- Безопасность нарушена.
- Система не работает.

**Действие:** немедленный откат.

### 5. Ошибка в архитектуре

- Решение не масштабируется.
- Решение не соответствует ADR.
- Решение создаёт долг.

**Действие:** обсудить с Архитектором, откатить.

---

## Уровни отката

### Уровень 1: Откат коммита

**Когда:** последний коммит сломал что-то.

**Как:**
```bash
git revert HEAD
```

**Плюсы:** безопасно, сохраняет историю.

**Минусы:** создаёт новый коммит.

### Уровень 2: Откат ветки

**Когда:** несколько коммитов в ветке сломали что-то.

**Как:**
```bash
git revert <commit1>..<commitN>
```

**Плюсы:** откатывает несколько коммитов.

**Минусы:** может быть сложно при конфликтах.

### Уровень 3: Сброс ветки

**Когда:** ветка не должна была существовать.

**Как:**
```bash
git reset --hard <commit>
git push --force-with-lease
```

**Плюсы:** чистая история.

**Минусы:** опасно, теряет коммиты.

**Правило:** использовать только в feature-ветках, не в main.

### Уровень 4: Откат merge

**Когда:** merge сломал main.

**Как:**
```bash
git revert -m 1 <merge-commit>
```

**Плюсы:** откатывает merge.

**Минусы:** сложно при повторном merge.

### Уровень 5: Откат релиза

**Когда:** релиз сломал production.

**Как:**
- Откатить на предыдущий тег.
- Пересобрать.
- Развернуть.

**Плюсы:** быстро.

**Минусы:** нужно иметь предыдущий релиз.

### Уровень 6: Откат миграции БД

**Когда:** миграция сломала данные.

**Как:**
- Применить down-миграцию.
- Если нет — восстановить из бэкапа.

**Правило:** все миграции должны иметь down-миграцию.

---

## Процедура отката

### Шаг 1: Определить проблему

- Что сломалось?
- Когда?
- Какой коммит?

**Инструменты:**
```bash
git log --oneline
git bisect
git blame
```

### Шаг 2: Определить уровень отката

- Один коммит — уровень 1.
- Несколько — уровень 2.
- Ветка — уровень 3.
- Merge — уровень 4.
- Релиз — уровень 5.
- Миграция — уровень 6.

### Шаг 3: Сделать бэкап

**Правило:** перед откатом — бэкап.

```bash
git branch backup-$(date +%Y%m%d-%H%M%S)
```

Для БД:
```bash
cp ~/.tensa/approval.db ~/.tensa/approval.db.bak
```

### Шаг 4: Откатить

Выполнить соответствующую команду.

### Шаг 5: Проверить

```bash
cargo fmt --check
cargo clippy -- -D warnings
cargo test
cargo build --release
```

Всё должно пройти.

### Шаг 6: Задокументировать

Написать в issue или PR:
- Что сломалось.
- Какой коммит.
- Как откатили.
- Что делать дальше.

### Шаг 7: Проанализировать

- Почему не получилось?
- Как избежать в будущем?
- Нужно ли обновить процесс?

---

## Что откатывать

### 1. Код

- `git revert` — безопасно.
- `git reset` — опасно.

### 2. Конфигурация

- Вернуть предыдущий `config.toml`.
- Вернуть предыдущий `apps.toml`.
- Вернуть предыдущий `secrets.toml`.

### 3. БД

- Применить down-миграцию.
- Восстановить из бэкапа.
- Откатить событие.

### 4. Модели

- Вернуть предыдущую версию модели.
- Пересобрать.

### 5. Зависимости

- Вернуть предыдущую версию в `Cargo.toml`.
- `cargo update -p <crate> --precise <version>`.

### 6. Релиз

- Откатить тег.
- Пересобрать.
- Развернуть.

---

## Что НЕ откатывать

### 1. Данные пользователя

Если откат кода ломает данные — **сначала бэкап**, потом откат.

### 2. Секреты

Секреты не откатываются через git. Они восстанавливаются из
защищённого хранилища.

### 3. Логи

Логи не откатываются. Они — история.

### 4. Внешние сервисы

Нельзя «откатить» отправленное письмо или сообщение в Telegram.

---

## Откат миграций БД

### 1. Все миграции должны иметь down

**Правило:** каждая up-миграция имеет down-миграцию.

```sql
-- up.sql
CREATE TABLE actions (...);

-- down.sql
DROP TABLE actions;
```

### 2. Откат через sqlx

```bash
sqlx migrate revert
```

### 3. Если down нет

- Восстановить из бэкапа.
- Написать down-миграцию.
- Применить.

### 4. Если данные потеряны

- Восстановить из бэкапа.
- Проанализировать, как избежать.
- Обновить процесс.

## Откат релиза

### 1. Определить предыдущий релиз

```bash
git tag --sort=-version:refname | head -5
```

### 2. Откатить

```bash
git checkout v0.1.0
```

### 3. Пересобрать

```bash
cargo build --release
```

### 4. Развернуть

- Windows: установить предыдущий `.msi`.
- Linux: установить предыдущий `.deb` / `.AppImage`.
- Android: установить предыдущий `.apk`.

### 5. Уведомить

- Пользователей.
- Команду.
- Архитектора.

---

## Откат на уровне данных

### 1. ApprovalStore

- События идемпотентны.
- Откат — через `apply_event` с обратным событием.
- Если нет — восстановить из бэкапа.

### 2. Память (Lance)

- Lance версионирует данные.
- Откат — через версию.
- Если нет — восстановить из Syncthing.

### 3. Заметки/контакты

- Soft delete.
- Откат — через `deleted = 0`.
- Если нет — восстановить из бэкапа.

### 4. Файлы

- Syncthing версионирует.
- Откат — через `.stversions/`.
- Если нет — восстановить из бэкапа.

## Пример: откат сломанного коммита

### 1. Проблема

CI упал на коммите `abc123`. Тесты не проходят.

### 2. Определение

```bash
git log --oneline
# abc123 Fix bug in request_action
# def456 Add tests
```

### 3. Бэкап

```bash
git branch backup-20261006-120000
```

### 4. Откат

```bash
git revert abc123
```

### 5. Проверка

```bash
cargo test
```

### 6. Документирование

```markdown
## Откат коммита abc123

**Что сломалось:** тесты в `tensa-approval`.
**Причина:** некорректная обработка `expires_at`.
**Откат:** `git revert abc123`.
**Что дальше:** исправить и повторить.
```

### 7. Анализ

- Почему тесты не были запущены локально?
- Как избежать?

**Решение:** добавить pre-commit hook.

## Пример: откат релиза

### 1. Проблема

Релиз `v0.2.0` ломает отправку почты.

### 2. Определение

Пользователи сообщают: «Письма не отправляются».

### 3. Бэкап

```bash
git branch backup-v0.2.0
```

### 4. Откат

```bash
git checkout v0.1.0
cargo build --release
```

### 5. Развернуть

- Windows: установить `v0.1.0.msi`.
- Linux: установить `v0.1.0.deb`.
- Android: установить `v0.1.0.apk`.

### 6. Уведомить

- Пользователей: «Откатили на v0.1.0. Исправляем».
- Архитектора: «Откат релиза. Причина: X».

### 7. Анализ

- Почему баг не поймали в CI?
- Как избежать?

**Решение:** добавить E2E-тест на отправку почты.

## Частые ошибки

### 1. Откат без бэкапа

**Плохо:** `git reset --hard` без бэкапа.

**Хорошо:** сначала `git branch backup-...`.

### 2. Откат данных без бэкапа

**Плохо:** откатить миграцию без бэкапа БД.

**Хорошо:** сначала `cp approval.db approval.db.bak`.

### 3. Откат без анализа

**Плохо:** откатил и забыл.

**Хорошо:** откатил и проанализировал.

### 4. Откат force push в main

**Плохо:** `git push --force` в main.

**Хорошо:** `git revert` в main.

### 5. Откат без документирования

**Плохо:** откатил, никто не знает почему.

**Хорошо:** написал в issue/PR.

### 6. Откат релиза без уведомления

**Плохо:** откатил, пользователи не знают.

**Хорошо:** уведомил пользователей.
