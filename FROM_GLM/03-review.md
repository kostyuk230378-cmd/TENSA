## Документация для GLM 5.3: `03-review.md`

```markdown
# Руководство для GLM 5.3 — Ревью

**Версия:** 0.1.0
**Дата:** 2026-10-06
**Статус:** Ревью

---

## Назначение

Этот документ описывает, как проходит ревью кода GLM 5.3 со стороны
Архитектора, и как GLM 5.3 должен готовить код к ревью.

Цель: минимизировать переделки, обеспечить качество, ускорить merge.

---

## Принципы

### 1. Ревью — часть процесса

Каждый коммит проходит ревью. Без ревью — нет merge.

### 2. Ревью — не критика

Ревью — это улучшение кода. GLM 5.3 не должен воспринимать замечания
как «ошибки», а как «обратную связь».

### 3. Ревью — двустороннее

Архитектор может ошибаться. Если GLM 5.3 считает, что замечание
некорректно — он должен **аргументировать**, а не молча исправлять.

### 4. Ревью — быстрое

Чем меньше коммит, тем быстрее ревью. Большие коммиты — долгое ревью.

### 5. Ревью — автоматизированное где возможно

CI проверяет:
- Форматирование.
- Линтинг.
- Тесты.
- Покрытие.

Архитектор проверяет:
- Архитектуру.
- Логику.
- Соответствие ТЗ.
- Безопасность.

---

## Что проверяет CI (автоматически)

### 1. Форматирование

```bash
cargo fmt --check
```

Если не проходит — GLM 5.3 должен запустить `cargo fmt`.

### 2. Линтинг

```bash
cargo clippy -- -D warnings
```

Если не проходит — GLM 5.3 должен исправить warnings.

### 3. Тесты

```bash
cargo test
```

Если не проходят — GLM 5.3 должен исправить.

### 4. Сборка

```bash
cargo build --release
```

Если не собирается — GLM 5.3 должен исправить.

### 5. Покрытие

```bash
cargo llvm-cov --fail-under-lines 80
```

Если ниже порога — GLM 5.3 должен добавить тесты.

### 6. Безопасность

```bash
cargo audit
```

Если есть уязвимости — GLM 5.3 должен обновить зависимости или
сообщить Архитектору.

---

## Что проверяет Архитектор (вручную)

### 1. Соответствие ТЗ

- Все пункты ТЗ выполнены.
- Ничего лишнего не добавлено.
- Сигнатуры соответствуют контрактам.

### 2. Архитектура

- Код следует ADR.
- Нет дублирования логики.
- Модули изолированы.
- Зависимости правильные.

### 3. Логика

- Алгоритм корректный.
- Граничные случаи обработаны.
- Ошибки обрабатываются.

### 4. Безопасность

- Секреты не логируются.
- ApprovalStore используется правильно.
- Выключатели работают.
- Нет `unwrap()` в production.

### 5. Стиль

- Именование понятное.
- Комментарии осмысленные.
- Нет мёртвого кода.
- Нет закомментированного кода.

### 6. Тесты

- Покрытие достаточное.
- Тесты осмысленные.
- Тесты детерминированные.

### 7. Документация

- Публичный API документирован.
- README обновлён.
- Примеры работают.

---

## Как GLM 5.3 готовит код к ревью

### 1. Прочитать ТЗ

Прочитай ТЗ полностью. Убедись, что все пункты выполнены.

### 2. Проверить контракты

Убедись, что сигнатуры соответствуют контрактам.

### 3. Запустить CI локально

```bash
cargo fmt --check
cargo clippy -- -D warnings
cargo test
cargo build --release
cargo llvm-cov --fail-under-lines 80
```

Все должны пройти.

### 4. Написать отчёт

```markdown
## Задача: [название]

### Статус
✅ Выполнено

### Что сделано
- [список]

### Тесты
- [список]
- Покрытие: X%

### Проверки
- `cargo fmt --check`: ✅
- `cargo clippy -- -D warnings`: ✅
- `cargo test`: ✅
- `cargo build --release`: ✅
- `cargo llvm-cov`: ✅ (X%)

### Что нужно уточнить
- [список]

### Файлы
- `crates/tensa-approval/src/sqlite.rs`
- `crates/tensa-approval/tests/integration.rs`
```

### 5. Приложить diff

Diff — это изменения в коде. GLM 5.3 должен приложить:
- `git diff` для изменённых файлов.
- Список новых файлов.

### 6. Ответить на замечания

Если Архитектор оставил замечания — GLM 5.3 должен:
- Ответить на каждое.
- Либо исправить, либо аргументировать.
- Не молчать.

---

## Формат замечаний Архитектора

```markdown
## Ревью: [название задачи]

### Общая оценка
✅ Принято / ⚠️ С замечаниями / ❌ Отклонено

### Замечания

#### 1. [Файл:строка]
**Проблема:** [описание]
**Как исправить:** [предложение]
**Приоритет:** Высокий / Средний / Низкий

#### 2. [Файл:строка]
...

### Что понравилось
- [список]

### Что нужно уточнить
- [список]
```

---

## Как GLM 5.3 отвечает на замечания

```markdown
## Ответ на ревью

### Замечание 1
**Принято.** Исправлено в коммите `abc123`.

### Замечание 2
**Принято с уточнением.** Исправлено, но также добавлен тест
на граничный случай.

### Замечание 3
**Не принято.** Аргументация: [почему].
Предлагаю обсудить.

### Замечание 4
**Вопрос.** Уточните, пожалуйста: [вопрос].
```

---

## Типы замечаний

### 1. Критичные (блокируют merge)

- Нарушение контракта.
- Нарушение ADR.
- Ошибка логики.
- Утечка секретов.
- Отсутствие тестов.

### 2. Важные (нужно исправить)

- Плохое именование.
- Дублирование кода.
- Отсутствие комментариев.
- Неоптимальный алгоритм.

### 3. Незначительные (можно отложить)

- Стиль.
- Форматирование.
- Мелкие улучшения.

### 4. Вопросы (нужно ответить)

- «Почему так?»
- «Что будет, если...?»
- «Пробовал ли...?»

---

## Что делать, если GLM 5.3 не согласен

### 1. Аргументировать

Не «я сделал так, потому что», а «я сделал так, потому что [факт]».

**Плохо:** «Мне так удобнее».

**Хорошо:** «Контракт 1 не запрещает это. Если запрещает — уточните, пожалуйста».

### 2. Предложить альтернативу

Не «не буду исправлять», а «предлагаю вместо этого [альтернатива]».

### 3. Спросить

Если неясно — спросить. Не додумывать.

### 4. Принять решение Архитектора

Если Архитектор настаивает — принять. Архитектор отвечает за продукт.

---

## Частые ошибки на ревью

### 1. Слишком большой коммит

**Плохо:** 1000 строк в одном коммите.

**Хорошо:** разбить на несколько коммитов.

### 2. Отсутствие тестов

**Плохо:** «Тесты потом».

**Хорошо:** тесты вместе с кодом.

### 3. Игнорирование CI

**Плохо:** «CI потом разберётся».

**Хорошо:** CI локально перед отправкой.

### 4. Молчание на замечания

**Плохо:** получить замечания и не ответить.

**Хорошо:** ответить на каждое.

### 5. Изменение сигнатур без обсуждения

**Плохо:** «Сигнатура неудобна — изменил».

**Хорошо:** «Сигнатура неудобна — предлагаю изменить».

### 6. Додумывание

**Плохо:** «В ТЗ не сказано — предположу».

**Хорошо:** «В ТЗ не сказано — спрошу».

## Пример полного цикла ревью

### 1. GLM 5.3 отправляет

```markdown
## Задача: Реализовать `SqliteApprovalStore::request_action`

### Статус
✅ Выполнено

### Что сделано
- Реализован метод `request_action`.
- Добавлены тесты (5 unit, 3 integration).
- Обновлён README.

### Проверки
- `cargo fmt --check`: ✅
- `cargo clippy -- -D warnings`: ✅
- `cargo test`: ✅
- `cargo build --release`: ✅
- `cargo llvm-cov`: ✅ (85%)

### Файлы
- `crates/tensa-approval/src/sqlite.rs`
- `crates/tensa-approval/tests/integration.rs`
```

### 2. Архитектор ревьюит

```markdown
## Ревью: request_action

### Общая оценка
⚠️ С замечаниями

### Замечания

#### 1. sqlite.rs:45
**Проблема:** Используется `unwrap()` на `Uuid::new_v4()`.
**Как исправить:** Использовать `Uuid::new_v4()` без `unwrap` (он не возвращает Result).
**Приоритет:** Средний

#### 2. sqlite.rs:60
**Проблема:** Логируется `payload`, который может содержать секреты.
**Как исправить:** Логировать только `action.id` и `action.kind`.
**Приоритет:** Высокий

#### 3. integration.rs:20
**Проблема:** Тест не проверяет `operation_id`.
**Как исправить:** Добавить проверку уникальности `operation_id`.
**Приоритет:** Низкий

### Что понравилось
- Чистая структура.
- Хорошие тесты.
- Понятные комментарии.
```

### 3. GLM 5.3 отвечает

```markdown
## Ответ на ревью

### Замечание 1
**Принято.** Исправлено в коммите `abc123`.

### Замечание 2
**Принято.** Исправлено, логируется только `id` и `kind`.

### Замечание 3
**Принято.** Добавлен тест на уникальность `operation_id`.
```

### 4. Архитектор принимает

```markdown
## Ревью: request_action (повторное)

### Общая оценка
✅ Принято

Все замечания исправлены. Merge.
```
