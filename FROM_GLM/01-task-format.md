## Документация для GLM 5.3: `01-task-format.md`

```markdown
# Руководство для GLM 5.3 — Формат задач

**Версия:** 0.1.0
**Дата:** 2026-10-06
**Статус:** Формат задач

---

## Назначение

Этот документ описывает, как Архитектор формулирует задачи для
GLM 5.3, и как GLM 5.3 должен их интерпретировать.

Цель: минимизировать неоднозначность, галлюцинации и переделки.

---

## Принципы

### 1. Задача — это контракт

Каждая задача — формальное обязательство. Если что-то неясно —
**спроси**, не додумывай.

### 2. Одна задача — один крейт (или модуль)

Не смешивай несколько крейтов в одной задаче. Если задача
затрагивает несколько — разбей на подзадачи.

### 3. Задача ссылается на документацию

Каждая задача должна ссылаться на:
- Соответствующий **ADR** (почему так).
- Соответствующий **контракт** (как взаимодействует).
- Соответствующее **ТЗ** (что делать).

### 4. Задача содержит критерии приёмки

Что считается «сделано»:
- Компилируется.
- Тесты проходят.
- Соответствует контракту.
- Документация обновлена.

### 5. Задача содержит ограничения

Что **не** делать:
- Не менять сигнатуры.
- Не добавлять зависимости без утверждения.
- Не использовать `unwrap()` в production.
- Не логировать секреты.

---

## Структура задачи

```markdown
# Задача: [краткое название]

## Контекст
[Зачем эта задача. Ссылки на ADR, контракты, ТЗ.]

## Что сделать
[Конкретные шаги. Список.]

## Что НЕ делать
[Ограничения.]

## Критерии приёмки
[Что считается «сделано».]

## Тесты
[Какие тесты написать.]

## Ссылки
- ADR-NNN
- Контракт N
- ТЗ: [крейт]
```

## Пример задачи

````markdown
# Задача: Реализовать `SqliteApprovalStore::request_action`

## Контекст

ApprovalStore — центральный элемент безопасности Tensa.
`request_action` создаёт новое действие в очереди одобрения.

Ссылки:
- ADR-001: Rust как язык ядра.
- ADR-012: gRPC (tonic) для синхронизации.
- Контракт 1: ApprovalStore (SQLite).
- ТЗ: tensa-approval.

## Что сделать

1. Реализовать метод `request_action` в `SqliteApprovalStore`:
   ```rust
   async fn request_action(&self, action: NewAction) -> Result<Action>;
   ```
2. Метод должен:
   - Проверить `max_pending_actions`.
   - Сгенерировать `id` (UUID v4).
   - Сгенерировать `operation_id` (UUID v4).
   - Вычислить `expires_at` = `created_at` + `action_ttl_hours * 3600`.
   - Записать в таблицу `actions`.
   - Записать событие `Created` в `action_events`.
   - Вернуть созданное действие.
3. Использовать `sqlx` для работы с SQLite.
4. Использовать `tracing` для логирования.

## Что НЕ делать

- Не выполнять действие — только создать запись.
- Не отправлять сетевые запросы.
- Не логировать `payload` (может содержать секреты).
- Не использовать `unwrap()` — только `Result`.

## Критерии приёмки

- Метод компилируется.
- Сигнатура соответствует контракту 1.
- Тесты проходят.
- `cargo clippy -- -D warnings` — без предупреждений.
- `cargo fmt --check` — без изменений.

## Тесты

1. **Unit:** создать действие, проверить поля.
2. **Unit:** превышение `max_pending_actions` → ошибка.
3. **Unit:** проверить `expires_at`.
4. **Integration:** создать действие, получить его через `get_by_id`.
5. **Integration:** проверить событие `Created` в `action_events`.
6. **Error:** невалидный `kind` → ошибка.

## Ссылки

- ADR-001, ADR-012.
- Контракт 1.
- ТЗ: tensa-approval.
````

## Как GLM 5.3 должен интерпретировать задачу

### Шаг 1: Прочитать задачу

Прочитай задачу **полностью**. Не начинай писать код, пока не
поймёшь:
- Что делать.
- Что не делать.
- Критерии приёмки.
- Тесты.

### Шаг 2: Прочитать документацию

Прочитай:
- Соответствующий **ADR**.
- Соответствующий **контракт**.
- Соответствующее **ТЗ**.

Если в задаче ссылка на ADR-NNN — прочитай его.

### Шаг 3: Проверить существующий код

Посмотри, что уже есть в крейте:
- Какие модули.
- Какие типы.
- Какие трейты.

Не дублируй. Используй существующее.

### Шаг 4: Написать код

Следуй:
- Сигнатурам из контракта.
- Структуре из ТЗ.
- Стилю из `00-overview.md`.

### Шаг 5: Написать тесты

Напиши тесты **до** или **вместе** с кодом. Не после.

### Шаг 6: Запустить проверки

```bash
cargo fmt --check
cargo clippy -- -D warnings
cargo test
cargo build --release
```

Все должны пройти.

### Шаг 7: Обновить документацию

Если изменил публичный API — обнови:
- Комментарии `///`.
- README крейта.
- Примеры.

### Шаг 8: Сообщить о результате

Сообщи Архитектору:
- Что сделано.
- Что протестировано.
- Что не получилось.
- Что нужно уточнить.

## Типы задач

### 1. Реализация

- Написать новый код.
- Следовать ТЗ.
- Написать тесты.

### 2. Рефакторинг

- Улучшить существующий код.
- Не менять поведение.
- Тесты должны проходить.

### 3. Исправление бага

- Найти причину.
- Исправить.
- Написать тест, который ловит баг.

### 4. Документация

- Написать/обновить документацию.
- Комментарии, README.

### 5. Тесты

- Написать тесты.
- Покрыть edge cases.

### 6. Исследование

- Изучить библиотеку.
- Сравнить альтернативы.
- Написать отчёт.

## Частые ошибки GLM 5.3

### 1. Додумывание

**Плохо:** «В ТЗ не указано, как обрабатывать ошибку — предположу, что нужно паниковать».

**Хорошо:** «В ТЗ не указано, как обрабатывать ошибку — спрошу Архитектора».

### 2. Изменение сигнатур

**Плохо:** «Сигнатура из контракта неудобна — изменю».

**Хорошо:** «Сигнатура из контракта неудобна — предложу изменение Архитектору».

### 3. Пропуск тестов

**Плохо:** «Код работает, тесты потом».

**Хорошо:** «Код + тесты вместе».

### 4. Использование `unwrap()`

**Плохо:** `let x = foo().unwrap();`

**Хорошо:** `let x = foo()?;` или `let x = foo().map_err(...)?;`

### 5. Логирование секретов

**Плохо:** `tracing::info!("Payload: {:?}", payload);`

**Хорошо:** `tracing::info!("Action created: {}", action.id);`

### 6. Дублирование кода

**Плохо:** копировать код из другого крейта.

**Хорошо:** использовать общий крейт (`tensa-core`).

### 7. Игнорирование CI

**Плохо:** «CI потом».

**Хорошо:** «CI с первого коммита».
