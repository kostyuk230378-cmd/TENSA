## ADR-001: Rust как язык ядра

**Статус:** Принято

**Контекст:**
Tensa — персональный ИИ-секретарь, работающий на нескольких узлах: десктоп (Windows, Linux), мобильный (Android), с точками входа для macOS и iOS. Система должна поддерживать: динамическое распределение ролей (heavy/thin), двустороннюю синхронизацию данных, локальный и облачный инференс LLM, работу в условиях разной производительности, долгосрочную поддерживаемость при разработке силами AI-ассистента (GLM 5.3) под архитектурным руководством человека.

Ключевое ограничение: логика ядра должна быть единой на всех платформах. Дублирование логики между Python (десктоп) и Kotlin/Swift (мобильный) создаёт долг. Python не компилируется под iOS/Android без костылей, Dart имеет слабую экосистему для сетевых операций, гибридные схемы ведут к дублированию.

**Решение:**
Выбран Rust для ядра в варианте «Rust + внешние сервисы»: ядро на Rust, сетевые операции через существующие крейты и внешние сервисы (teloxide/tdlib, himalaya, lettre, caldav, reqwest).

Обоснование:
- Единая логика на всех узлах критична для динамических ролей и синхронизации.
- Кросс-платформенность из коробки сохраняет точки входа для macOS и iOS без переписывания.
- Строгая типизация снижает риск ошибок, когда код пишет AI-ассистент.
- Производительность важна для LLM-инференса и синхронизации.
- Долгосрочная поддерживаемость: один код, один набор тестов, единый протокол.

Роль GLM 5.3 как основного разработчика и человека как Архитектора учитывается при выборе: Rust даёт больше гарантий корректности при генерации кода AI, чем Python или Dart.

**Последствия:**

Положительные:
- Один код ядра для всех платформ.
- Один набор тестов.
- Единый протокол синхронизации.
- Легко добавлять новые платформы.
- Точки входа для macOS и iOS сохраняются автоматически.
- Строгая типизация помогает AI-ассистенту.

Отрицательные:
- Требуются компетенции в Rust.
- Сборка сложнее: кросс-компиляция под Android (NDK), iOS (Xcode), Windows (MSVC), Linux (GCC/Clang), macOS.
- FFI-мосты (uniffi, JNI, C FFI) — источник багов.
- Некоторые крейты менее зрелые, чем Python-аналоги (CalDAV, Telegram).
- Время разработки больше, чем на Python/Dart.

Отложено / точки входа:
- Ничего.

**Связанные ADR:**
- ADR-002, ADR-003, ADR-006, ADR-007, ADR-008, ADR-009.

## ADR-002: Rust + внешние сервисы

**Статус:** Принято

**Контекст:**
Ядро Tensa написано на Rust (ADR-001). Ядру нужны сетевые операции: Telegram (приём команд, отправка уведомлений, кнопки одобрения), почта (IMAP/SMTP), календарь (CalDAV), WhatsApp (Cloud API, отложено), WoL (отложено).

Для каждого направления есть два пути: писать своё на Rust с нуля, или использовать существующие решения — крейты на Rust или внешние сервисы (C/C++/Go-бинарники) с FFI.

Ключевое ограничение: код пишет AI-ассистент (GLM 5.3). Чем меньше кода пишется с нуля, тем меньше риск ошибок и тем быстрее разработка. Но внешние зависимости добавляют риск: незрелые крейты, проблемы с кросс-компиляцией, безопасность.

**Решение:**
Выбран гибридный подход: Rust-ядро + внешние сервисы для сетевых операций.

| Направление | Решение | Обоснование |
|---|---|---|
| Telegram | teloxide (Rust) или tdlib (C++ через FFI) | teloxide — чистый Rust, проще; tdlib — надёжнее, но сложнее |
| IMAP | himalaya (Rust) или imap crate | himalaya — зрелый, поддерживает IDLE |
| SMTP | lettre (Rust) | Зрелый, безопасный |
| CalDAV | caldav crate или собственный клиент | Крейт может быть незрелым — проверить |
| WhatsApp | reqwest (Rust) к Cloud API | Простой HTTP-клиент |
| WoL | Собственный (UDP) | Тривиально, не нужен крейт |

Обоснование выбора:
- Минимум кода с нуля — меньше риск ошибок AI.
- Зрелые крейты там, где есть (lettre, reqwest).
- Собственные обёртки там, где крейты незрелые (CalDAV, возможно Telegram).
- Точки входа для замены: если крейт не подходит — заменить на свой или на внешний сервис.

**Последствия:**

Положительные:
- Меньше кода писать с нуля.
- Быстрее разработка.
- Зрелые крейты протестированы сообществом.
- Меньше риск ошибок AI.

Отрицательные:
- Больше зависимостей — нужно следить за поддержкой и безопасностью.
- Некоторые крейты могут не собираться под Android/iOS — нужно проверять в CI.
- Незрелые крейты (CalDAV) могут требовать собственных обёрток.
- Разные лицензии — нужно проверять совместимость.

Отложено / точки входа:
- WhatsApp: reqwest-клиент, интерфейс WhatsAppProvider объявлен, реализация NoOp в MVP.
- WoL: UDP-модуль, интерфейс WolProvider объявлен, реализация NoOp в MVP.
- Telegram: если teloxide не подойдёт — переход на tdlib через FFI.

**Связанные ADR:**
- ADR-001, ADR-003, ADR-004, ADR-005, ADR-006.

## ADR-003: FFI к llama.cpp

**Статус:** Принято

**Контекст:**
Ядро Tensa (ADR-001) должно запускать локальную LLM для: офлайн-работы, снижения стоимости, приватности, fallback при сбое облака.

Модель для десктопа: TheStageAI/gemma-4-E2B-it-GGUF (XS/S/M) в формате GGUF. Для Android: LiteRT (отдельный ADR).

Движок для десктопа: llama.cpp — C++ библиотека с C API, поддерживающая GGUF, квантование, CPU/GPU-инференс. Зрелая, активно развивается.

Ключевые ограничения:
1. Код пишет AI-ассистент (GLM 5.3). C API llama.cpp — это unsafe-код с ручным управлением памятью. Ошибки в FFI приводят к segfault, утечкам памяти, гонкам. Нужен безопасный и стабильный слой поверх C API.
2. llama.cpp активно развивается. API меняется между версиями, поведение инференса может меняться. Без контроля версий возможны: внезапная несовместимость API, регресс в качестве, проблемы с кросс-компиляцией.

**Решение:**
Выбран прямой FFI к llama.cpp с двухуровневой архитектурой и контролем версий + автообновлением с подтверждением.

Уровень 1: tensa-llama-sys — raw FFI-биндинги.
- Генерируются через bindgen из заголовков llama.cpp.
- Тонкий слой, минимум логики.
- Все вызовы — unsafe.
- Изоляция: ни один unsafe-вызов не выходит за пределы этого крейта.

Уровень 2: tensa-llama — безопасная обёртка.
- Публичный API на безопасном Rust.
- RAII для ресурсов (модель, контекст, сессия).
- Обработка ошибок через Result, не через панику.
- Асинхронный API (tokio) для интеграции с ядром.
- Тесты на утечки памяти, гонки, граничные случаи.

Уровень 3: Контроль версий и автообновление.
- Фиксация версии llama.cpp в Cargo.toml как git-зависимость (тег или коммит-хэш).
- Проверка новых версий при запуске ядра (или периодически) — запрос к GitHub API.
- Автообновление с подтверждением (вариант B):
  1. Tensa обнаруживает новую версию.
  2. Уведомляет пользователя.
  3. Пользователь подтверждает.
  4. Tensa скачивает новую версию.
  5. Пересобирает tensa-llama-sys.
  6. Запускает тесты совместимости (smoke-тесты на инференс).
  7. Если тест прошёл — обновление применяется.
  8. Если тест не прошёл — откат и уведомление.

Обоснование:
- Прямой FFI даёт полный контроль над версией llama.cpp и параметрами инференса.
- Двухуровневая архитектура изолирует unsafe в одном крейте.
- RAII гарантирует освобождение ресурсов.
- Result вместо паники — предсказуемое поведение.
- Асинхронность — интеграция с tokio-ядром.
- Фиксация версии в Cargo.toml — воспроизводимость сборки.
- Автообновление с подтверждением — баланс между актуальностью и контролем.

Рассмотренные альтернативы (кратко):
- llama-cpp-rs — готовые биндинги, но менее контролируемые.
- candle — Rust-фреймворк от Hugging Face, но требует конвертации моделей.
- ort (ONNX Runtime) — не поддерживает GGUF, требует ONNX-моделей.

**Последствия:**

Положительные:
- Полный контроль над инференсом.
- Безопасный API для остального ядра.
- Изоляция unsafe в одном крейте.
- Асинхронность — интеграция с tokio.
- Возможность тонкой настройки (квантование, контекст, sampling).
- Контроль версий защищает от внезапных несовместимостей.
- Автообновление с подтверждением позволяет оставаться на актуальной версии без риска.
- Откат при неудаче — безопасность.

Отрицательные:
- Нужно писать и поддерживать FFI-обёртку.
- bindgen требует заголовков llama.cpp — нужно следить за версиями.
- Сборка llama.cpp под все платформы (Windows, Linux, Android) — сложнее, чем чистый Rust.
- Тестирование unsafe-кода требует дисциплины (miri, sanitizers, valgrind).
- Автообновление требует механизма отката и тестов совместимости — дополнительная сложность.
- Обновление llama.cpp может ломать API — нужно версионировать и тестировать.

Отложено / точки входа:
- GPU-ускорение (CUDA, Metal, Vulkan) — в MVP только CPU, GPU добавляется позже.
- LiteRT для Android — отдельный ADR.
- Облачная LLM (OpenRouter) — отдельный ADR (роутер).
- Автообновление — включается по настройке, по умолчанию выключено в MVP.

**Связанные ADR:**
- ADR-001, ADR-002, ADR-006, ADR-007.

## ADR-004: Lance для векторного поиска

**Статус:** Принято

**Контекст:**
Ядро Tensa (ADR-001) должно выполнять поиск по файлам: семантический поиск, гибридный поиск (семантика + ключевые слова), работа офлайн, синхронизация между узлами, работа на устройствах с разной производительностью.

Модель эмбеддингов: intfloat/multilingual-e5-small (ADR-005). Размерность: 384. Префиксы: query: для запросов, passage: для документов.

Ключевые ограничения:
1. Синхронизация. Индексы должны синхронизироваться между узлами. Это исключает embedded-решения без версионирования (например, ChromaDB embedded).
2. Файловая природа. Индексы должны храниться в файлах, чтобы Syncthing мог их синхронизировать.
3. Версионирование. Нужна история изменений, чтобы разрешать конфликты (LWW по mtime) и откатывать.
4. Кросс-платформенность. Работа на Windows, Linux, Android.
5. Производительность. Быстрый поиск на целевых объёмах (до 100K документов).

**Решение:**
Выбран Lance (LanceDB) как движок векторного поиска.

Lance — это формат колоночного хранения данных с поддержкой векторных индексов, версионирования и репликации. Реализован на Rust, имеет крейт lance.

Обоснование:
- Файловая природа — данные хранятся в файлах, Syncthing может их синхронизировать.
- Версионирование — Lance поддерживает версии данных, что позволяет разрешать конфликты и откатывать.
- Rust-крейт — нативная интеграция с ядром (ADR-001).
- Кросс-платформенность — работает на Windows, Linux, Android.
- Производительность — колоночное хранение + векторные индексы дают быстрый поиск.
- Гибридный поиск — можно комбинировать векторный поиск с полнотекстовым.

Индекс по умолчанию — Flat (brute-force). Обоснование: целевые объёмы для персонального секретаря — до 100K документов. Для этих объёмов Flat даёт приемлемое время поиска и не требует обучения индекса. IVF-PQ и HNSW могут быть добавлены позже, если объёмы вырастут.

Версия крейта: **lance 13.0** (версия 0.9 из раннего плана не компилируется на rustc 1.98 — конфликт arrow-arith 50 с chrono). LanceDB-стиль (Connection::open, create_table) в Rust-крейте lance не существует. Реальный Rust-API: `Dataset::open`, `Dataset::write`, `dataset.scan().nearest()`, `dataset.delete()`.

Рассмотренные альтернативы (кратко):
- ChromaDB embedded — не подходит для синхронизации.
- Qdrant — требует сервера, избыточно.
- usearch / hnswlib-rs — только векторный индекс, без хранения и версионирования.
- SQLite + расширение для векторов — менее зрелое.

**Производительность:**
Целевые объёмы: маленькая коллекция (100–1 000 документов, ~10K чанков), средняя (1 000–10 000 документов, ~100K чанков).

Ожидаемое время поиска (top-10, 384 dim, CPU, Flat):

| Объём | Десктоп (x86, AVX2) | Android (ARM, NEON) |
|---|---|---|
| 10K | 5–20 мс | 10–50 мс |
| 100K | 50–200 мс | 100–500 мс |

Вывод: CPU достаточно для целевых объёмов. GPU-ускорение не требуется в MVP.

**Последствия:**

Положительные:
- Файловая природа — Syncthing синхронизирует.
- Версионирование — разрешение конфликтов, откат.
- Rust-крейт — нативная интеграция.
- Кросс-платформенность.
- Производительность CPU достаточна.
- Гибридный поиск.
- Flat-индекс — простой, точный, не требует обучения.

Отрицательные:
- Lance относительно молодой проект — нужно следить за развитием.
- Документация может быть неполной.
- На Android размер индексов может быть значительным — нужно тестировать.
- Синхронизация Lance-файлов через Syncthing требует аккуратности.
- Нужно проектировать схему данных.
- Flat-индекс на больших объёмах (>100K) может быть медленным.

Отложено / точки входа:
- GPU-ускорение векторного поиска — не нужно для целевых объёмов.
- IVF-PQ и HNSW — добавить, если объёмы превысят 100K векторов.
- Распределённый поиск между узлами — в MVP только локальный поиск + on-demand sync.
- Полнотекстовый поиск через FTS5 — может быть добавлен позже.

**Связанные ADR:**
- ADR-001, ADR-002, ADR-005.

## ADR-005: fastembed-rs для эмбеддингов

**Статус:** Принято

**Контекст:**
Ядро Tensa (ADR-001) должно генерировать эмбеддинги для: индексации документов (passage-эмбеддинги), поисковых запросов (query-эмбеддинги), работы офлайн, кросс-платформенности.

Модель: intfloat/multilingual-e5-small.
- Размерность: 384.
- Мультиязычная: русский + английский.
- Размер: ~130 МБ.
- Префиксы: query: для запросов, passage: для документов (обязательны).

Ключевые ограничения:
1. Rust-интеграция. Ядро на Rust (ADR-001), нужен Rust-крейт или FFI.
2. Кросс-платформенность. Windows, Linux, Android.
3. Офлайн-работа. Модель должна работать локально.
4. Производительность. Индексация тысяч чанков не должна занимать часы.
5. Префиксы. Модель требует query:/passage: — нужно автоматически добавлять.

**Решение:**
Выбран fastembed-rs как движок для генерации эмбеддингов.

fastembed-rs — это Rust-порт fastembed (от Qdrant), поддерживающий ONNX Runtime и популярные модели эмбеддингов, включая multilingual-e5.

Обоснование:
- Rust-крейт — нативная интеграция с ядром (ADR-001).
- Поддержка multilingual-e5 — модель из наших требований.
- ONNX Runtime — кросс-платформенный, работает на Windows, Linux, Android.
- Автоматическая загрузка моделей — fastembed-rs умеет скачивать модели при первом запуске.
- Кэширование — эмбеддинги кэшируются, повторные запросы быстрее.
- Батчинг — можно генерировать эмбеддинги пачками, что ускоряет индексацию.

Версия крейта: **fastembed 7.1**. API: `TextInitOptions::new(EmbeddingModel::MultilingualE5Small)`, синхронный `TextEmbedding::try_new`, `embed(texts, Some(batch))` требует `&mut self` → `Arc<Mutex<TextEmbedding>>` внутри `spawn_blocking`.

Префиксы: fastembed-rs не добавляет префиксы автоматически. Обёртка tensa-memory/embed должна явно добавлять query: или passage: в зависимости от контекста.

Рассмотренные альтернативы (кратко):
- sentence-transformers (Python) — не подходит для Rust-ядра.
- ONNX Runtime напрямую — возможно, но fastembed-rs удобнее.
- candle — Rust-фреймворк от Hugging Face, но требует конвертации моделей.
- Вызов удалённого сервиса эмбеддингов — противоречит офлайн-работе.

**Последствия:**

Положительные:
- Rust-крейт — нативная интеграция.
- Поддержка multilingual-e5.

- Автоматическая загрузка моделей.

## ADR-006: uniffi для FFI-мостов

**Статус:** Принято

**Контекст:**
Ядро Tensa написано на Rust (ADR-001). UI написан на других языках: десктоп — Svelte через Tauri (Rust-бэкенд, JS-фронтенд), Android — Flutter (Dart) + нативные плагины (Kotlin), PWA — Svelte (JS).

Ядру нужно предоставить API для UI: отправка запросов, получение очереди одобрений, одобрение/отклонение, поиск по файлам, настройки, статус узлов.

Ключевые ограничения:
1. Кросс-платформенность. API должен работать на Windows, Linux, Android.
2. Типизация. Ошибки в FFI-мостах приводят к крашам, утечкам, гонкам. Нужна строгая типизация.
3. Асинхронность. Ядро асинхронное (tokio), UI тоже.
4. Код пишет AI. Чем меньше ручного FFI-кода, тем меньше ошибок.
5. Долгосрочная поддерживаемость. Изменения в API не должны требовать ручного обновления мостов на каждом языке.

**Решение:**
Выбран uniffi для генерации FFI-мостов.

uniffi — это инструмент от Mozilla, который генерирует биндинги для Kotlin, Swift, Python и других языков из Rust-кода. Описание интерфейса — через UDL (UniFFI Definition Language) или proc-macros.

Обоснование:
- Автоматическая генерация биндингов — меньше ручного кода.
- Строгая типизация — ошибки ловятся на этапе генерации.
- Поддержка async — uniffi умеет работать с async Rust.
- Кросс-платформенность — Kotlin (Android), Swift (iOS, позже), Python (для CLI).
- Активная поддержка — Mozilla использует uniffi в Firefox.
- Меньше ошибок AI — GLM 5.3 пишет Rust-код, uniffi генерирует биндинги.

Что uniffi не покрывает:
- Tauri IPC — десктопный UI (Svelte) общается с Rust через Tauri IPC, не через uniffi. Tauri сам генерирует биндинги для JS/TS.
- JNI для Android — uniffi генерирует Kotlin-биндинги, но Flutter (Dart) общается с Kotlin через MethodChannel. Нужен промежуточный слой.
- PWA — JS-фронтенд общается с ядром через HTTP/gRPC, не через uniffi.

Схема:
```
Десктоп (Svelte) → Tauri IPC (JS) → Rust (Tauri)
Android (Flutter) → MethodChannel (Dart ↔ Kotlin) → Kotlin (uniffi) → Rust
PWA (Svelte) → HTTP/gRPC → Rust (HTTP)
```

Рассмотренные альтернативы (кратко):
- jni-rs — только для Android, ручной FFI, много кода.
- C FFI вручную — для Swift (iOS), много ручного кода.
- pyo3 — только для Python (CLI), не для мобильного.
- swig — устаревший, не для Rust.
- cbindgen — генерирует C-заголовки, но не биндинги для Kotlin/Swift.

**Последствия:**

Положительные:
- Автоматическая генерация биндингов.
- Строгая типизация — меньше ошибок.
- Поддержка async.
- Кросс-платформенность (Kotlin, Swift, Python).
- Меньше ручного FFI-кода.
- Активная поддержка Mozilla.

Отрицательные:
- uniffi требует описания интерфейса (UDL или proc-macros) — дополнительная работа.
- Не все типы Rust поддерживаются — нужно следить за совместимостью.
- Async в uniffi может быть незрелым — нужно тестировать.
- Для Flutter нужен промежуточный слой (MethodChannel).
- Для PWA нужен HTTP/gRPC-слой.
- uniffi версии могут ломать API — нужно версионировать.

Отложено / точки входа:
- Swift-биндинги (iOS) — uniffi поддерживает, но iOS вне MVP.
- Python-биндинги (CLI) — uniffi поддерживает.
- Прямой JNI для Android — если uniffi не подойдёт, fallback на jni-rs.
- C FFI для Swift — если uniffi не подойдёт, fallback на ручной C FFI.

**Связанные ADR:**
- ADR-001, ADR-002, ADR-003, ADR-007.

## ADR-007: Cargo workspace + CI

**Статус:** Принято

**Контекст:**
Ядро Tensa — Rust-проект (ADR-001), состоящий из множества крейтов: tensa-core, tensa-sync, tensa-approval, tensa-router, tensa-perf, tensa-nodes, tensa-tools, tensa-llm, tensa-memory, tensa-ffi, tensa-cli.

Целевые платформы MVP: Windows (x86_64-pc-windows-msvc), Linux (x86_64-unknown-linux-gnu), Android (aarch64-linux-android, armv7-linux-androideabi).

Точки входа (компиляция проверяется, но не используется): macOS (x86_64-apple-darwin, aarch64-apple-darwin), iOS (aarch64-apple-ios, x86_64-apple-ios-sim).

Ключевые ограничения:
1. Много крейтов. Нужна единая структура, общие зависимости, единые версии.
2. Кросс-компиляция. Android требует NDK, iOS требует Xcode, Windows требует MSVC.
3. CI. Нужна автоматическая сборка, тесты, релизы под каждую платформу.
4. Код пишет AI. CI ловит ошибки AI до того, как они попадут в релиз.
5. Долгосрочная поддерживаемость. Добавление новых крейтов и платформ не должно требовать переписывания CI.

**Решение:**
Выбран Cargo workspace для структуры проекта и GitHub Actions с матрицей платформ для CI.

Cargo workspace:
- Единый Cargo.toml в корне с [workspace].
- Все крейты — в crates/.
- Общие зависимости — в [workspace.dependencies].
- Единые версии зависимостей для всех крейтов.
- Общие настройки профилей (release, dev).

Структура:
```
tensa/
├── Cargo.toml
├── Cargo.lock
├── crates/
│   ├── tensa-core/
│   ├── tensa-sync/
│   ├── tensa-approval/
│   ├── tensa-router/
│   ├── tensa-perf/
│   ├── tensa-nodes/
│   ├── tensa-tools/
│   ├── tensa-llm/
│   ├── tensa-memory/
│   ├── tensa-ffi/
│   └── tensa-cli/
├── apps/
│   ├── desktop/
│   ├── android/
│   └── pwa/
├── docs/
└── .github/
    └── workflows/
```

CI: GitHub Actions с матрицей платформ.

| Платформа | Target | Runner | Назначение |
|---|---|---|---|
| Windows | x86_64-pc-windows-msvc | windows-latest | Сборка, тесты, релиз |
| Linux | x86_64-unknown-linux-gnu | ubuntu-latest | Сборка, тесты, релиз |
| Android | aarch64-linux-android | ubuntu-latest + NDK | Сборка, тесты |
| Android | armv7-linux-androideabi | ubuntu-latest + NDK | Сборка |
| macOS | x86_64-apple-darwin | macos-latest | Проверка сборки |
| macOS | aarch64-apple-darwin | macos-latest | Проверка сборки |
| iOS | aarch64-apple-ios | macos-latest | Проверка сборки |

Этапы CI:
1. Проверка форматирования: cargo fmt --check.
2. Линтинг: cargo clippy -- -D warnings.
3. Сборка: cargo build --release --target <target>.
4. Тесты: cargo test --target <target>.
5. Кросс-компиляция: для Android — NDK, для iOS/macOS — Xcode.
6. Релиз: артефакты под каждую платформу (при теге).
7. Кэширование: Cargo registry, target, NDK, Xcode.

Релизы:
- При теге v* — сборка артефактов под все платформы.
- Windows: .exe / .msi (Tauri).
- Linux: .deb / .AppImage (Tauri).
- Android: .apk (Flutter).
- macOS: .dmg (Tauri) — точка входа.
- iOS: .ipa — точка входа.

Рассмотренные альтернативы (кратко):
- Отдельные репозитории для крейтов — сложнее, нет единого lock-файла.
- GitLab CI — не выбран, GitHub удобнее для open-source.
- CircleCI, Travis — менее популярны.
- Собственный CI — избыточно.

**Последствия:**

Положительные:
- Единая структура проекта.
- Единые версии зависимостей.
- Единый lock-файл.
- Автоматическая сборка под все платформы.
- CI ловит ошибки AI до релиза.
- Кэширование ускоряет CI.
- Релизы автоматизированы.

Отрицательные:
- Cargo workspace может быть медленным на больших проектах.
- Кросс-компиляция под Android/iOS требует настройки NDK/Xcode.
- CI может быть дорогим (macOS runners дороже).
- Нужно следить за версиями Rust, NDK, Xcode.
- Добавление новых платформ требует обновления CI.

Отложено / точки входа:
- macOS-релизы — только проверка сборки в MVP, релизы позже.
- iOS-релизы — только проверка сборки в MVP, релизы позже.
- Windows ARM64 — не в MVP.
- Linux ARM64 — не в MVP.
- Docker-образы для сборки — можно добавить позже.

**Связанные ADR:**
- ADR-001, ADR-002, ADR-003, ADR-006.

## ADR-011: Syncthing как библиотека

**Статус:** Принято

**Контекст:**
Синхронизация — ключевая функция Tensa. Синхронизируются: ApprovalStore (постоянно, через gRPC), память/заметки/контакты (по требованию, через gRPC), файлы (постоянно, через Syncthing).

Файлы — это пользовательские документы, вложения из почты, результаты работы секретаря.

Ключевые ограничения:
1. P2P. Файлы не должны уходить в облако.
2. Кросс-платформенность. Windows, Linux, Android.
3. Двусторонняя синхронизация.
4. Конфликты. Нужна политика разрешения.
5. Управление из Rust-ядра.
6. Android. Foreground service для фоновой работы.

Рассмотренные альтернативы:
- Syncthing — P2P, зрелый, кроссплатформенный.
- Resilio Sync — проприетарный.
- Собственный P2P на Rust — огромная работа.
- Rclone — для облака.
- Git-annex — сложно.
- Nextcloud — требует сервера.

**Решение:**
Выбран Syncthing как движок синхронизации файлов. Syncthing включается в дистрибутив Tensa как библиотека.

Что делаем:
1. Windows/Linux: Syncthing-бинарник в Tauri bundle (externalBin), запускается как sidecar.
2. Android: syncthing-android включается в APK как библиотека.
3. Конфигурация: Tensa генерирует config.xml при первом запуске.
4. Управление: через REST API (http://localhost:8384/rest/...).
5. Мониторинг: статус через REST API.
6. Конфликты: Tensa слушает события Syncthing и реагирует на .sync-conflict-* файлы.

Схема:
```
Rust Core (libtensa)
├── tensa-sync/files
│   ├── REST-клиент к Syncthing
│   ├── Генерация config.xml
│   ├── Мониторинг статуса
│   └── Обработка конфликтов
Syncthing (sidecar / библиотека)
├── Windows/Linux: бинарник
└── Android: syncthing-android (библиотека)
Tailscale (сеть)
```

**Последствия:**

Положительные:
- P2P — файлы не уходят в облако.
- Зрелый, проверенный движок.
- Кросс-платформенность.
- Двусторонняя синхронизация.
- Управление из Rust-ядра.
- Пользователь не видит отдельного приложения.

Отрицательные:
- Размер дистрибутива вырастет (~15–25 МБ).
- На Android интеграция Syncthing — самая сложная часть MVP.
- Foreground service для Syncthing + foreground service для Tensa = два уведомления. Нужно объединить.
- Обновление Syncthing внутри APK — сложнее.
- REST API Syncthing может меняться.
- Конфликты файлов требуют политики и UI.

Отложено / точки входа:
- Собственный P2P на Rust — если Syncthing не подойдёт.
- Resilio Sync — если понадобится скорость.
- Замена Syncthing — интерфейс FileSyncProvider объявлен.
- Шифрование файлов at rest — после MVP.

**Связанные ADR:**
- ADR-001, ADR-002, ADR-007, ADR-018.

## ADR-012: gRPC (tonic) для синхронизации

**Статус:** Принято

**Контекст:**
Tensa — распределённая система. Синхронизируются: ApprovalStore (постоянно), память/заметки/контакты (по требованию), метаданные файлов, статус узлов.

Узлы: десктоп (Windows, Linux), Android. Связь — через Tailscale.

Ключевые ограничения:
1. Типизация. Ошибки в протоколе приводят к потере данных, дублям, конфликтам.
2. Кросс-платформенность. Windows, Linux, Android.
3. Rust-ядро. Протокол должен быть нативным для Rust.
4. Async. Ядро асинхронное (tokio).
5. Идемпотентность. Повторные операции не должны ломать состояние.
6. On-demand sync. Телефон запрашивает данные у ПК только когда нужно.

Рассмотренные альтернативы:
- gRPC (tonic) — типизированный, эффективный, стриминг.
- REST (axum) — проще, но менее эффективный.
- WebSocket — для стриминга, но сложнее.
- JSON-RPC — простой, но менее типизированный.
- Cap'n Proto — быстрее Protobuf, но менее зрелый в Rust.
- FlatBuffers — быстрее, но сложнее.

**Решение:**
Выбран gRPC через tonic для синхронизации.

Что делаем:
1. Protobuf-схема (.proto) — описание сервисов и сообщений.
2. Кодогенерация через tonic-build и prost.
3. Транспорт — HTTP/2 поверх Tailscale (mTLS или WireGuard).
4. Стриминг — server streaming, client streaming, bidirectional.
5. Идемпотентность — operation_id (UUID).
6. Аутентификация — mTLS или токены.

Сервисы: SyncService, NodeService, DataService, VoiceService, QueryService.

Схема:
```
Узел A (десктоп)
├── gRPC-сервер (tonic)
└── gRPC-клиент (tonic)
Tailscale (HTTP/2, mTLS)
Узел B (Android)
├── gRPC-сервер (tonic)
└── gRPC-клиент (tonic)
```

**Последствия:**

Положительные:
- Типизированный протокол.
- Эффективность Protobuf.
- Стриминг.
- Кодогенерация.
- Нативная интеграция с Rust (tonic).
- Async — интеграция с tokio.
- Идемпотентность.

Отрицательные:
- Нужно писать .proto-файлы.
- Нужно настраивать tonic-build в build.rs.
- Нужно настраивать mTLS.
- Для Android — grpc-kotlin + protobuf-kotlin.
- gRPC сложнее в отладке, чем REST.
- Версионирование .proto — нужно следить за совместимостью.

Отложено / точки входа:
- REST для PWA — если понадобится.
- GraphQL — не нужен.
- gRPC-Web для браузера — если PWA потребует.
- mTLS — можно начать с Tailscale-шифрования.

**Связанные ADR:**
- ADR-001, ADR-002, ADR-007, ADR-011.

## ADR-013: On-demand синхронизация

**Статус:** Принято

**Контекст:**
Tensa — распределённая система. Синхронизируются: ApprovalStore (постоянно), память/заметки/контакты (по требованию), файлы (через Syncthing).

Почему on-demand для памяти/заметок/контактов:
- Телефон не всегда имеет полную копию данных ПК.
- Постоянная синхронизация — трафик, батарея, конфликты.
- Пользователь редко открывает старые заметки.

Ключевые ограничения:
1. ПК постоянно включён — можно всегда запросить данные.
2. Телефон может быть офлайн — нужен кэш.
3. ПК может быть недоступен.
4. Консистентность.
5. Производительность.

Рассмотренные альтернативы:
- Постоянная синхронизация всего — трафик, батарея.
- Только локальные данные — телефон не видит данные ПК.
- On-demand — выбран.
- Гибрид (кэш + on-demand) — часть решения.

**Решение:**
Выбрана on-demand синхронизация с локальным кэшем.

Что делаем:
1. Локальный кэш на телефоне — LRU-кэш последних запросов.
2. Запрос данных — при новом запросе: если в кэше — использовать; если нет — запросить у ПК через gRPC; если ПК офлайн — использовать кэш + предупредить.
3. Инвалидация кэша — при изменении данных на ПК, ПК шлёт уведомление через gRPC-стриминг.
4. TTL кэша — настраиваемый (по умолчанию 1 час).
5. Приоритеты — часто используемые данные кэшируются дольше.
6. Локальная индексация — если телефон heavy.

Сервис (gRPC): DataService.GetNotes, GetContacts, SearchFiles, GetApprovalQueue.

Схема:
```
Телефон (Android)
├── UI
├── Локальный кэш (LRU)
└── gRPC-клиент
Tailscale
ПК (десктоп)
├── gRPC-сервер
├── Данные (память, заметки, контакты)
└── Источник истины
```

**Последствия:**

Положительные:
- Меньше трафика.
- Меньше батареи.
- Меньше конфликтов.
- Проще.
- ПК — источник истины.
- Инвалидация через gRPC-стриминг.

Отрицательные:
- Если ПК офлайн — телефон видит только кэш.
- Нужен механизм инвалидации.
- Нужен LRU-кэш.
- TTL кэша — нужно настраивать.
- Приоритеты кэша — нужно проектировать.
- Если телефон heavy — отдельная логика.

Отложено / точки входа:
- CRDT для конфликтов — если LWW не хватит.
- Полная репликация — если понадобится.
- Распределённый поиск между узлами — после MVP.
- Локальная индексация на телефоне — если телефон heavy.

**Связанные ADR:**
- ADR-001, ADR-004, ADR-011, ADR-012.

## ADR-014: Фоновые задачи на Android

**Статус:** Принято

**Контекст:**
Android — полноценный узел Tensa. На Android должны работать: Telegram-бот, почта (IMAP/SMTP), Syncthing, ApprovalStore, синхронизация данных, LLM (если телефон heavy).

Android ограничивает фоновые процессы: Doze mode, App Standby, Background execution limits, Battery optimization (агрессивные убийцы процессов).

Push-уведомления (VPS + FCM) исключены. Значит, фоновые задачи решаются через WorkManager и Foreground Service.

Ключевые ограничения:
1. Надёжность. Telegram-бот должен работать, даже если приложение свёрнуто.
2. Батарея. Нельзя тратить батарею впустую.
3. Задержка. Сообщения могут приходить с задержкой.
4. Производители. Агрессивные убийцы процессов.
5. Одно уведомление. Syncthing + Tensa не должны показывать два уведомления.

Рассмотренные альтернативы:
- Foreground Service — надёжно, но уведомление висит.
- WorkManager — экономит батарею, но задержка 15+ минут.
- Push (FCM) — исключено.
- Гибрид — выбран.

**Решение:**
Выбран гибридный подход: Foreground Service + WorkManager.

Что делаем:
1. Foreground Service — когда телефон заряжается или пользователь явно включил «мгновенные ответы»: Telegram-бот polling, IMAP IDLE, Syncthing, синхронизация ApprovalStore. Одно объединённое уведомление «Tensa работает».
2. WorkManager — когда телефон от батареи или пользователь выбрал «экономить батарею»: Telegram polling (15+ минут), IMAP polling, Syncthing, ApprovalStore sync.
3. Настройка в UI: «Мгновенные ответы» / «Экономить батарею» / «Автоматически».
4. Объединённое уведомление.
5. Обход убийц процессов — инструкция для пользователя.

Схема:
```
Tensa (Android)
├── UI (Flutter)
├── Foreground Service (объединённый)
│   ├── Telegram-бот
│   ├── IMAP IDLE
│   ├── Syncthing
│   └── ApprovalStore sync
├── WorkManager (периодический)
│   ├── Telegram polling
│   ├── IMAP polling
│   └── ApprovalStore sync
└── Rust Core (libtensa)
```

**Последствия:**

Положительные:
- Надёжность при Foreground Service.
- Экономия батареи при WorkManager.
- Гибкость — пользователь выбирает режим.
- Одно уведомление вместо двух.
- Работает без VPS и FCM.

Отрицательные:
- Задержка при WorkManager (15+ минут).
- Уведомление висит при Foreground Service.
- Производители Android могут убивать процессы.
- Пользователь должен настроить battery optimization.
- Foreground Service + WorkManager — сложнее.
- Тестирование на разных производителях.

Отложено / точки входа:
- Push (FCM) — если понадобится мгновенная доставка.
- VPS — если понадобится централизованная инфраструктура.
- iOS Background Tasks — после MVP.
- Оптимизация батареи — после MVP.

**Связанные ADR:**
- ADR-001, ADR-008, ADR-011, ADR-012, ADR-013.

## ADR-015: Почта напрямую, несколько ящиков

**Статус:** Принято

**Контекст:**
Tensa должна работать с почтой: чтение (IMAP), отправка (SMTP), черновики, синхронизация.

MVP (v0.1): один почтовый ящик. После MVP (v0.2+): несколько ящиков (личный, рабочий).

На ПК и телефоне — один почтовый ящик (в MVP). Пользователь хочет видеть одни и те же письма на обоих устройствах.

Ключевые ограничения:
1. Один ящик, два узла (MVP).
2. Несколько ящиков (v0.2+).
3. Конфликты. Флаги, черновики, отправка.
4. Идемпотентность.
5. Приватность. Письма не должны уходить в облако Tensa (нет шлюза).
6. Офлайн. Телефон может быть офлайн.
7. Работа без ПК. Телефон отправляет напрямую.

Рассмотренные альтернативы:
- Tensa-шлюз для почты — противоречит privacy-first.
- Прямая работа с IMAP/SMTP — выбран.
- Только через ПК — телефон не может отправлять без ПК.
- Облачный сервис — противоречит privacy-first.

**Решение:**
Выбрана прямая работа с IMAP/SMTP с обоих узлов, без Tensa-шлюза, с архитектурой, поддерживающей несколько ящиков (v0.2+).

Модель данных:
```
Account {
    id: String,
    label: String,
    imap_host, imap_port, imap_user, imap_password,
    smtp_host, smtp_port, smtp_user, smtp_password,
    default: bool
}
AccountStore {
    accounts: Vec<Account>,
    default_account_id: String
}
```

Отправка:
- Каждое действие отправки указывает account_id.
- Если не указан — ящик по умолчанию.
- Флаг allow_email_send может быть на ящик.

Чтение:
- Каждый ящик — отдельное IMAP-соединение.
- Каждый ящик — отдельный SMTP-клиент.
- Каждый ящик — отдельная очередь отправки.

Индексация:
- Письма из разных ящиков индексируются в одну коллекцию Lance с полем account_id.

Идемпотентность отправки:
- Каждое письмо имеет X-Tensa-Send-Id (UUID).
- Перед отправкой — проверка, не отправлено ли уже.

Черновики:
- Создаются через APPEND с уникальным Message-ID.
- Не создавать черновики на обоих узлах одновременно.

Флаги:
- IMAP-сервер сам синхронизирует флаги.

Очередь отправки:
- Если узел офлайн — письмо в очередь.
- При подключении — отправка.
- Очередь синхронизируется через ApprovalStore.

Управление соединениями:
- Схема «активное соединение + standby».
- В каждый момент только один узел держит активное соединение.
- При необходимости — сигнал на прерывание.
- Активным остаётся используемый узел.
- Определение используемого узла — гибрид (таймаут + явный сигнал).
- Конфликт — очередь.
- TTL настраиваемый (по умолчанию 15 минут).

Конфигурация:
```toml
[email]
default_account = "personal"

[[email.accounts]]
id = "personal"
label = "Личный"
imap_host = "imap.example.com"
imap_port = 993
imap_user = "user@example.com"
# imap_password — читается из окружения (IMAP_PASSWORD)
smtp_host = "smtp.example.com"
smtp_port = 587
smtp_user = "user@example.com"
# smtp_password — читается из окружения (SMTP_PASSWORD)
```

**Последствия:**

Положительные:
- Privacy-first — нет шлюза.
- Работа без ПК — телефон отправляет напрямую.
- Простота — нет центрального сервера.
- IMAP-сервер синхронизирует флаги.
- Очередь отправки — офлайн-работа.
- Архитектура готова к нескольким ящикам.
- Обход ограничений сервера без центрального шлюза.
- Активным остаётся используемый узел.

Отрицательные:
- Конфликты черновиков.
- Идемпотентность отправки — дополнительная логика.
- Два IMAP-соединения — сервер может ограничивать.
- Два SMTP-соединения — сервер может ограничивать.
- На Android — himalaya через Rust (uniffi) или нативный Kotlin-клиент.
- Очередь отправки — дополнительная логика.
- Если почтовый сервер не поддерживает IDLE — polling.
- Несколько ящиков в v0.2+ — дополнительная сложность.
- Передача соединения — дополнительная логика (gRPC-сигналы).
- Таймауты — нужно настраивать.
- Если оба узла активно используются — очередь.
- Определение используемого узла — эвристика.

Отложено / точки входа:
- Несколько ящиков — v0.2+.
- Объединённый inbox — v0.2+.
- IDLE на Android — если сервер поддерживает.
- Push-уведомления о новых письмах — после MVP.
- Синхронизация черновиков — если понадобится.
- Шифрование писем (PGP) — после MVP.
- Приоритеты узлов — если очередь окажется неудобной.
- Разделение IMAP/SMTP между узлами — если сервер позволяет.

**Связанные ADR:**
- ADR-001, ADR-002, ADR-004, ADR-011, ADR-012.

## ADR-016: ПК постоянно включён, WoL отложен

**Статус:** Принято

**Контекст:**
Tensa — распределённая система. Узлы: десктоп (Windows, Linux) — heavy-узел, Android — heavy или thin.

Для синхронизации и on-demand запросов нужен доступ к данным. Если ПК выключен — телефон не может запросить данные.

Wake-on-LAN (WoL) — технология пробуждения ПК по сети.

Ключевые ограничения:
1. WoL через Tailscale не работает напрямую — Tailscale не пропускает broadcast.
2. WoL требует relay в LAN — устройство в той же локальной сети, что и ПК.
3. WoL требует настройки BIOS/UEFI — не все ПК поддерживают.
4. WoL требует настройки ОС — Windows/Linux должны разрешить пробуждение.
5. WoL не всегда надёжен.

Почему WoL сложен:
1. WoL через Tailscale не работает напрямую.
2. WoL требует relay в LAN — обычно одноплатник (Raspberry Pi, Orange Pi).
3. WoL на Windows особенно капризен: BIOS/UEFI, сетевая карта, отключение Fast Startup, драйверы, роутеры.
4. WoL на Linux — проще, но тоже требует настройки (ethtool, systemd).
5. WoL не всегда надёжен.

Вывод: WoL — это не «просто отправить пакет», а целая инфраструктура. Поэтому логично отложить.

**Решение:**
ПК постоянно включён. WoL отложен до v0.2+.

Что делаем:
1. ПК работает 24/7.
2. Энергосбережение — настройки ОС: отключить сон, отключить гибернацию, разрешить пробуждение по сети.
3. Документация docs/always_on_setup.md.
4. Мониторинг — Tensa проверяет доступность ПК.
5. Точка входа для WoL — интерфейс WolProvider объявлен, реализация NoOp в MVP.

Схема:
```
ПК (десктоп) — работает 24/7
├── Tensa-ядро
├── gRPC-сервер
├── Данные (источник истины)
└── Tailscale
Tailscale
Android — работает когда включён
├── Tensa-ядро
├── gRPC-клиент
└── Кэш данных
```

**Последствия:**

Положительные:
- Простота — не нужно настраивать WoL.
- Надёжность — ПК всегда доступен.
- On-demand sync работает всегда.
- Heavy-узел всегда доступен.
- Меньше кода в MVP.

Отрицательные:
- Энергопотребление — ПК работает 24/7.
- Износ оборудования.
- Шум — если ПК в жилой комнате.
- Стоимость электричества.
- Если ПК выключен (сбой) — телефон в degraded mode.
- WoL отложен.

Отложено / точки входа:
- WoL — v0.2+. Интерфейс WolProvider объявлен.
- Одноплатник (Raspberry Pi, Orange Pi) как relay в LAN — v0.2+.
- Настройка Windows для WoL — v0.2+.
- Настройка Linux для WoL — v0.2+.
- Будильник — v0.2+.
- Автоматическое пробуждение — v0.2+.

**Связанные ADR:**
- ADR-001, ADR-012, ADR-013, ADR-014.

## ADR-017: Запуск приложений

**Статус:** Принято

**Контекст:**
Tensa должна уметь открывать файлы и запускать приложения: открытие файлов ассоциированными приложениями, запуск приложений по имени, открытие файла в конкретном приложении, из почты (вложение), по команде.

Целевые платформы: Windows, Linux, Android.

Ключевые ограничения:
1. Безопасность. LLM не должна запускать произвольные команды. Только из белого списка или через ApprovalStore.
2. Кроссплатформенность. Разные API.
3. Белый список. Приложения должны быть явно разрешены.
4. Аудит. Все запуски логируются.
5. ApprovalStore. Запуск из ненадёжного источника — через одобрение.

Рассмотренные альтернативы:
- Только открытие файлов и ссылок (уровень A) — просто, но ограниченно.
- Открытие файлов + запуск приложений по имени (уровень B) — выбран.
- Полноценный лаунчер (уровень C) — требует автоматизации UI.

**Решение:**
Выбран уровень B: открытие файлов + запуск приложений по имени.

Что делаем:
1. Платформо-специфичные реализации:
   - Windows: start, ShellExecute, ассоциации реестра.
   - Linux: xdg-open, .desktop-файлы, MIME-ассоциации.
   - Android: Intent с ACTION_VIEW, PackageManager.
2. Белый список приложений: ~/.tensa/apps.toml.
3. Открытие файлов: ассоциированное приложение по MIME-типу.
4. Открытие файла в конкретном приложении.
5. Из почты: вложение → ассоциированное приложение.
6. Безопасность: белый список, ApprovalStore, логирование.
7. Аудит: ~/.tensa/logs/apps.log.

Схема:
```
Rust Core (libtensa)
├── tensa-tools/apps
│   ├── Windows: ShellExecute, start
│   ├── Linux: xdg-open, .desktop
│   └── Android: Intent, PackageManager
├── Белый список (apps.toml)
├── ApprovalStore (для ненадёжных источников)
└── Аудит (apps.log)
```

**Последствия:**

Положительные:
- Удобство — можно запускать приложения по имени.
- Безопасность — белый список, ApprovalStore, аудит.
- Кросс-платформенность.
- Интеграция с почтой.
- Интеграция с LLM.

Отрицательные:
- Нужны платформо-специфичные реализации.
- Белый список нужно настраивать.
- На Android PackageManager может не находить приложения.
- На Linux .desktop-файлы могут быть нестандартными.
- На Windows ассоциации реестра могут быть изменены.
- Аудит — дополнительная логика.

Отложено / точки входа:
- Полноценный лаунчер (уровень C) — v0.2+.
- Автоматизация UI — v0.2+.
- Запуск с параметрами — v0.2+.
- Макросы — v0.2+.

**Связанные ADR:**
- ADR-001, ADR-002, ADR-012, ADR-015.

## ADR-018: Синхронизация файлов через Syncthing

**Статус:** Принято

**Контекст:**
Tensa — распределённая система. Файлы — ключевая часть: пользовательские документы, вложения из почты, результаты работы секретаря.

Файлы должны синхронизироваться между узлами: десктоп (Windows, Linux), Android.

Syncthing выбран как движок (ADR-011). Этот ADR описывает, как именно файлы синхронизируются.

Ключевые ограничения:
1. Что синхронизируется. Не всё.
2. Конфликты. Syncthing создаёт .sync-conflict-* файлы.
3. Индексация. Когда файл синхронизирован — проиндексировать.
4. Безопасность. Файлы на телефоне могут быть украдены.
5. Производительность. Большие файлы — долго.
6. Пользовательские файлы. Где они лежат.

**Решение:**
Синхронизация файлов через Syncthing с чёткими правилами.

Что синхронизируется:

| Каталог | Синхронизируется | Обоснование |
|---|---|---|
| ~/.tensa/files/ | ✅ | Пользовательские документы |
| ~/.tensa/notes/ | ✅ | Заметки |
| ~/.tensa/attachments/ | ✅ | Вложения из почты |
| ~/.tensa/generated/ | ✅ | Сгенерированные документы |
| ~/.tensa/models/ | ❌ | Каждый узел скачивает сам |
| ~/.tensa/chroma/ | ❌ | Lance-индексы синхронизируются через gRPC |
| ~/.tensa/logs/ | ❌ | Логи локальные |
| ~/.tensa/cache/ | ❌ | Кэш локальный |
| ~/.tensa/config.toml | ❌ | Секреты вводятся на каждом узле |

Конфликты:
- LWW по mtime — побеждает более свежий файл.
- Сохранение обеих версий — конфликтный файл переименовывается.
- Уведомление пользователя.
- UI для разрешения.
- Автоматическое разрешение — если файлы идентичны по хэшу.

Индексация:
- Syncthing генерирует событие.
- Tensa слушает событие.
- Tensa индексирует файл (Lance).
- Если файл — вложение из почты, связывается с письмом.

Безопасность:
- Шифрование at rest — опционально (v0.2+).
- Remote wipe — v0.2+.
- Аудит.

Производительность:
- Большие файлы — Syncthing синхронизирует по частям.
- Индексация — в фоне.
- Прогресс — через SSE или gRPC-стриминг.

Пользовательские файлы:
- Каталог по умолчанию: ~/.tensa/files/.
- Пользователь может добавить свои каталоги.
- Белый список расширений: .txt, .pdf, .docx, .md.
- Исключения: .tmp, .cache, .log.

Схема:
```
Десктоп (Tensa)
├── ~/.tensa/files/ (Syncthing)
├── ~/.tensa/notes/ (Syncthing)
├── ~/.tensa/attachments/ (Syncthing)
└── tensa-sync/files (REST-клиент к Syncthing)
Syncthing (P2P, Tailscale)
Android (Tensa)
├── ~/.tensa/files/ (Syncthing)
├── ~/.tensa/notes/ (Syncthing)
├── ~/.tensa/attachments/ (Syncthing)
└── tensa-sync/files (REST-клиент к Syncthing)
```

**Последствия:**

Положительные:
- P2P — файлы не уходят в облако.
- Двусторонняя синхронизация.
- Конфликты решаются.
- Индексация автоматическая.
- Пользовательские файлы — гибко.
- Прогресс — через SSE/gRPC.

Отрицательные:
- Конфликты требуют UI.
- Большие файлы — долго.
- На Android — Foreground Service для Syncthing.
- Шифрование at rest — отложено.
- Remote wipe — отложен.
- Аудит — дополнительная логика.
- Белый список расширений — нужно настраивать.

Отложено / точки входа:
- Шифрование at rest — v0.2+.
- Remote wipe — v0.2+.
- Пользовательские каталоги — v0.2+.
- Исключения — v0.2+.
- Автоматическое разрешение конфликтов — v0.2+.

## ADR-019: OCR-движок

**Статус:** Принято

**Контекст:**
Tensa работает с документами (PDF, DOCX, XLSX, PPTX, изображения). Часть из них — сканированные (нет текстового слоя), для них нужен OCR.

Требования: русский язык, чистый Rust, CPU, кросс-платформенность, Android SDK, iOS SDK (после MVP), структура документа, либеральная лицензия, скорость менее секунды, низкие накладные расходы.

Рассмотренные варианты:
- RustO! (byrizki/rusto-rs) — MIT, чистый Rust, MNN, PP-OCRv6, Android/iOS SDK.
- oar-ocr (GreatV/oar-ocr) — Apache-2.0, Rust + ONNX Runtime, PP-OCRv6.
- franken_ocr (Dicklesworthstone) — MIT + rider, чистый Rust, PDF.
- PaddleOCR + Paddle Lite — C++/Java, не Rust.

**Решение:**
Выбран RustO! (byrizki/rusto-rs) как основной OCR-движок.

Обоснование:
- MIT — чисто юридически для коммерческого Tensa.
- Чистый Rust — нативная интеграция с ядром.
- MNN (Alibaba) — лёгкий, быстрый.
- PP-OCRv6 — современная модель.
- Android SDK — готовый (Kotlin + AAR).
- iOS SDK — готовый (Swift + XCFramework).
- React Native, .NET, C FFI.
- Структура — многоколоночные таблицы, счета, формы.
- Скорость — менее секунды.
- Память — низкие накладные расходы.

Русский язык:
- RustO! не имеет русского «из коробки».
- Но технически поддерживает: движок читает ppocr_keys.txt.
- Cyrillic OCR от PaddleOCR — модель для кириллицы.
- Покрывает: русский, украинский, белорусский, болгарский, македонский, сербский, казахский, киргизский, монгольский + английский + цифры + спецсимволы.
- Конвертация: PaddleOCR → ONNX → MNN через convert_paddle_to_mnn.py.
- Конвертация при сборке Tensa (CI).

Альтернатива: oar-ocr (Apache-2.0).
Референс: franken_ocr (MIT + rider) — изучить архитектуру.

**Последствия:**

Положительные:
- MIT — чисто юридически.
- Чистый Rust — нативная интеграция.
- MNN — лёгкий, быстрый.
- PP-OCRv6 — современная модель.
- Android/iOS SDK — готовые.
- Структура — таблицы, счета, формы.
- Скорость — менее секунды.
- Мультиязычность.

Отрицательные:
- Русский — не «из коробки», нужна конвертация.
- Python — для конвертации (только в CI).
- Конвертация при сборке — дополнительный шаг.
- Cyrillic OCR — нужно тестировать качество.
- RustO! — относительно новый проект.

Отложено / точки входа:
- oar-ocr — альтернатива.
- franken_ocr — только референс.
- PaddleOCR + Paddle Lite — fallback для Android.
- Тестирование русского — при разработке.
- Другие языки — Cyrillic OCR покрывает.

## ADR-021: Иерархическая память (Letta-style) на Rust

**Статус:** Принято

**Контекст:**
Tensa — персональный ИИ-секретарь. Ему нужна память, которая:
- Помнит владельца (имя, предпочтения, язык).
- Помнит персону секретаря (как его называть, роль).
- Помнит историю разговоров.
- Помнит документы (долговременное хранилище).
- Может обновляться агентом (LLM).

Текущая архитектура (ADR-004, ADR-005) покрывает:
- Векторный поиск по документам (Lance).
- Эмбеддинги (fastembed-rs).

Но не покрывает:
- Персону агента (как называть секретаря).
- Информацию о владельце (имя, предпочтения).
- Историю разговоров (recall).
- Иерархию памяти (core / recall / archival).

Существующие решения:
- Mem0 — слой памяти, но Python, нет core memory.
- Letta (MemGPT) — иерархическая память, но Python/TypeScript.
- LangGraph / CrewAI — избыточно, Python, не для одного агента.

Ключевое ограничение: код пишет AI-ассистент (GLM 5.3). Нужна чистая Rust-реализация, без Python-зависимостей.

Рассмотренные альтернативы:
- Mem0 — Python, нет core memory.
- Letta (MemGPT) — Python/TypeScript, тяжёлый.
- LangGraph / CrewAI — избыточно.
- Своя реализация на Rust — выбран.

**Решение:**
Выбрана своя реализация иерархической памяти на Rust, вдохновлённая моделью Letta (MemGPT).

### Четыре уровня памяти

**1. Core memory (SQLite)**
- Всегда в контексте LLM.
- Структурированные блоки:
  - persona — персона секретаря (как называть, роль).
  - human — информация о владельце (имя, предпочтения, язык).
  - tasks — текущие задачи.
  - preferences — предпочтения владельца.
- Редактируется агентом через tool calls:
  - core_memory_replace — заменить блок.
  - core_memory_append — добавить в блок.
- Хранится в SQLite (~/.tensa/memory.db).
- Размер ограничен (например, 2000 токенов).

**2. Recall memory (SQLite)**
- Полная история разговоров.
- Поиск по истории (FTS5).
- Не всегда в контексте — извлекается по запросу.
- Хранится в SQLite (~/.tensa/memory.db).
- Агент может искать через recall_memory_search.

**3. Archival memory (Lance)**
- Долговременное хранилище (документы, факты).
- Векторный поиск (Lance, ADR-004).
- Не всегда в контексте — извлекается по запросу.
- Агент может искать через archival_memory_search.
- Агент может добавлять через archival_memory_insert.

**4. Message buffer (в памяти)**
- Скользящее окно последних сообщений.
- Не хранится на диске.
- Используется для контекста LLM.

### Схема

```
┌─────────────────────────────────────────────────────┐
│  LLM (Gemma 4 E2B / 26B A4B)                        │
│  ┌───────────────────────────────────────────────┐  │
│  │  Контекст:                                    │  │
│  │  ├── System prompt                            │  │
│  │  ├── Core memory (persona, human, tasks)      │  │
│  │  ├── Message buffer (последние сообщения)     │  │
│  │  └── Retrieved memories (recall + archival)   │  │
│  └───────────────────────────────────────────────┘  │
└──────────────────┬──────────────────────────────────┘
                   │
                   │ Tool calls
                   ▼
┌─────────────────────────────────────────────────────┐
│  Memory Manager (Rust)                              │
│  ├── CoreMemory (SQLite)                            │
│  │   ├── persona                                    │
│  │   ├── human                                      │
│  │   ├── tasks                                      │
│  │   └── preferences                                │
│  ├── RecallMemory (SQLite + FTS5)                   │
│  │   └── история разговоров                         │
│  └── ArchivalMemory (Lance)                         │
│      └── документы, факты                           │
└─────────────────────────────────────────────────────┘
```

### Tool calls для памяти

**Core memory:**
- core_memory_replace(block: string, value: string) — заменить блок.
- core_memory_append(block: string, value: string) — добавить в блок.

**Recall memory:**
- recall_memory_search(query: string, limit: number) — поиск по истории.

**Archival memory:**
- archival_memory_search(query: string, limit: number) — поиск по архиву.
- archival_memory_insert(content: string, tags: [string]) — добавить в архив.

### Файл памяти при первом запуске

При первом запуске Tensa создаёт core memory blocks:

persona:
```
Я — Tensa, персональный ИИ-секретарь. Моя задача — помогать
владельцу управлять документами, почтой, календарём, Telegram и
приложениями. Я работаю на русском и английском языках. Я не
выполняю действия без одобрения владельца. Я уважаю приватность и
не передаю данные третьим лицам.
```

human:
```
Владельца зовут {owner_name}. Он предпочитает обращение
«{owner_title}». Его язык: {language}. Часовой пояс: {timezone}.
```

tasks:
```
Активные задачи: {active_tasks}
```

preferences:
```
Владелец предпочитает: {preferences}
```

### Что это даёт

- Персона — секретарь знает, как его называть.
- Владелец — секретарь знает, как обращаться.
- История — секретарь помнит разговоры.
- Архив — секретарь помнит документы.
- Обновление — агент сам редактирует память.

### Что это требует

- SQLite для core и recall.
- Lance для archival (уже есть).
- Memory Manager на Rust.
- Tool calls в LLM.
- Ограничение размера core memory.

**Последствия:**

Положительные:
- Чистый Rust — нет Python-зависимостей.
- Персона секретаря — как называть.
- Информация о владельце — имя, предпочтения.
